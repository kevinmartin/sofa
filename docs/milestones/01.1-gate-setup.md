## Create the scoped GitHub App

Register a private GitHub App owned by Kevin's account and install it on **selected repositories** `kevinmartin/sofa` and `kevinmartin/sofa-disposable` only. Disable the webhook unless an operator specifically needs it; the gate uses REST API calls, not App webhooks. Give the App repository permissions `Actions: Read and write`, `Commit statuses: Read and write`, `Pull requests: Read-only`, and `Contents: Read-only` (plus GitHub's automatic `Metadata: Read-only`). It does not need Administration, Secrets, Workflows, Projects, Deployments, or repository deletion rights. The disposable coordinator's Project/issue and publication permissions remain separate.

The following two Actions environments were created with `main`-only branch policies. Confirm those policies before inserting any App key:

| Repository | Environment | Selected deployment branch | Environment secrets |
| --- | --- | --- | --- |
| `sofa` | `sofa-gate-dispatch` | `main` only | `SOFA_GATE_APP_ID`, `SOFA_GATE_APP_PRIVATE_KEY` |
| `sofa-disposable` | `sofa-gate-coordinator` | `main` only | `SOFA_GATE_APP_ID`, `SOFA_GATE_APP_PRIVATE_KEY`, `SOFA_DISPOSABLE_WORKFLOW_TOKEN` |

Operator steps (enter credentials in GitHub, never in an issue, PR, chat, or workflow log):

1. In Kevin's account **Settings → Developer settings → GitHub Apps**, register a new private App. Use the sofa repository URL as its homepage, choose **Only on this account**, turn the webhook **Active** switch off, and assign only the repository permissions above. Install it with **Only select repositories** and select the two named repositories. Record its numeric App ID, then generate one private key. [Registering a GitHub App](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app)
2. In each repository's **Settings → Environments**, open the already-created environment in the table and confirm its sole deployment branch rule is the branch `main`. Add `SOFA_GATE_APP_ID` with the numeric ID and `SOFA_GATE_APP_PRIVATE_KEY` with the full generated PEM, including its begin/end lines, as **environment secrets** in both environments. Do not also create repository-level copies. [Environment secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets#creating-secrets-for-an-environment)
3. In Kevin's **Settings → Developer settings → Personal access tokens → Fine-grained tokens**, create a short-lived token whose resource owner is `kevinmartin` and whose only selected repository is `sofa-disposable`. Give it `Contents: Read and write` and `Workflows: Read and write`. Add it only as the `SOFA_DISPOSABLE_WORKFLOW_TOKEN` environment secret in `sofa-disposable` → `sofa-gate-coordinator`. [Fine-grained tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token), [workflow-file permission](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens#repository-permissions-for-workflows)
4. Confirm the **secret names**, App ID, selected installations, and branch rules without revealing either credential. The coordinator's next scheduled scan will create and run an exact suite. The manual dispatch described below remains a recovery control.

Use **Selected branches and tags** with a single *branch* rule `main`, not “Protected branches only” while sofa has no protection rule. Do not add a tag rule or `refs/pull/*/merge`. The key belongs in environment secrets, not repository secrets: a same-repository PR can alter its `pull_request` workflow, but its merge ref cannot enter a `main`-only environment. The trusted sofa `workflow_run` bridge has `GITHUB_REF` on the default branch and only reads live PR metadata. Its job declares `deployment: false`, so it can use the environment without creating deployment history. [GitHub environment branch rules](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments), [workflow_run ref behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run)

The sofa bridge mints an installation token narrowed further to the disposable repository with only `actions:write` and `metadata:read`, then dispatches `sofa-gate.yml` with current PR number, candidate head SHA, base SHA, and source run identity. The disposable coordinator independently re-reads the PR, verifies the candidate artifact and real disposable draft PR, and mints a distinct sofa-repository token with `statuses:write` to publish context `sofa / hosted-e2e`. Its read-only job token inspects runs and artifacts; the existing `SOFA_PUBLISH_TOKEN` makes only the bounded disposable Git/PR writes from the trusted `main` job. Candidate jobs never receive either token, key, Project token, or publisher token. The existing repository-level publisher secret should be moved into a separately restricted trusted-job environment during a later credential migration; do not pass it through candidate jobs.

The coordinator must create a temporary `.github/workflows/` file in **sofa-disposable**. Its first hosted run, [36063384387](https://github.com/kevinmartin/sofa-disposable/actions/runs/36063384387), reached this write and failed: the job's `GITHUB_TOKEN` has `contents:write` but cannot author workflow files. A separate fine-grained token restricted to `kevinmartin/sofa-disposable` with `Contents: Read and write` and `Workflows: Read and write` has since been configured as `SOFA_DISPOSABLE_WORKFLOW_TOKEN` in the `main`-only `sofa-gate-coordinator` environment. It is used only for the owned Git tree, commit, and ref creation requests. Read-only discovery and dispatch continue to use the short-lived job token. Do not give this authoring token access to sofa or place it in a repository-level secret. If the token is absent, a new suite fails before a write; an existing exact suite branch can still be inspected. A future App installation with the same narrow disposable workflow permission can replace the fine-grained token.

## Pilot, then require the App source

1. Run the disposable-default-branch scheduled watcher on the current PR #2 head/base. A manual dispatch is a recovery control. Confirm the coordinator performed the hosted scenarios and posted `sofa / hosted-e2e` from the new App on the **exact candidate head SHA**. Capture its report and linked disposable run; a status alone is not evidence that the suite ran.
2. After Kevin merges PR #1, rebase PR #2 onto `main`, then run the hosted suite again. Treat every new head or base SHA as a new pair. Confirm a failed or absent suite leaves the current pair blocked, and that a passing suite posts a new App-sourced status for that pair.
3. Enable protection for sofa `main` with required status checks in **strict/up-to-date** mode. Require context `sofa / hosted-e2e` from the specific App ID. Also require the `sofa PR fast / deterministic` check from GitHub Actions if available. Preserve Kevin's review/merge policy; the gate does not merge PRs. The REST branch-protection representation uses `required_status_checks.strict: true` and `checks: [{"context":"sofa / hosted-e2e","app_id":<actual App ID>}]`; set other protection fields deliberately rather than replacing existing rules blindly. [GitHub required-check source and strictness](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [REST representation](https://docs.github.com/en/rest/branches/branch-protection)
4. Prove the rule on PR #2: a controlled failing status from the App blocks merge, a fresh passing status for the current head/base clears only the check requirement, and moving the parent/base invalidates the older green result until the PR is updated and retested. Inspect the actual mergeability and required-check source; do not infer enforcement from configuration alone.

The bridge is installed by merging 01.1, so the disposable scheduled watcher is the bootstrap for PR #2 and remains the fallback if a `workflow_run` event is delayed or omitted. A missing dispatch or App key means no green status. Do not create a user-token status, run candidate code in the privileged bridge, mark a stale pair passing, or enable a source-agnostic required context as a fallback.

# Milestone 02.1 — Major-version workflows and CLI distribution

## Summary

Consumers select `@v0` or eventually `@v1` once. Each job that uses the CLIs downloads the latest promoted release within that major version when it starts. Updates require no consumer workflow edits, source builds, or maintained checksum pins.

Use moving major tags, immutable semantic-version releases, and GitHub’s signed release-asset verification. Preserve an optional source-build path for hosted testing of unmerged Sofa changes.

Requires milestones 01.1 and 02. Publish Linux amd64 binaries initially. Automatically release validated merges into `main`; stable v1 activation remains an owner-controlled decision after qualification.

## Major channels and releases

- Use moving `v0` and `v1` tags as release channels. Do not create branches or GitHub Releases with those names.
- Use immutable exact-version tags and GitHub Releases such as `v0.1.0` and `v1.2.3`.
- Start with release series `0.1`. Each validated main merge creates the next patch version. Minor or major series changes require a reviewed configuration change.
- Build both CLIs from the approved source revision, embedding their version and source revision. Publish one Linux amd64 bundle containing `sofa`, `sofa-test`, and release metadata.
- Upload all assets before publishing the immutable release. Run the disposable canary before advancing the major tag.
- Update the major tag directly, without deleting it first. Serialize promotion and guard the update against an unexpected previous ref.
- Restrict major-tag updates to release automation. Protect exact-version tags from modification and deletion.

The major tag identifies the **current promoted release**, rather than whichever release was published most recently. A failed or unfinished canary therefore cannot become a consumer’s “latest” CLI.

Retries must recognize an existing release for the source revision, avoid allocating duplicate versions, and resume incomplete promotion. Failed releases remain unpromoted; their assets and version tags are never replaced.

Recover through a reviewed forward fix, including a PR revert when appropriate. A revert creates a new main commit and a new immutable release; the normal quality, canary and queued promotion path advances the major channel to it. A release that fails before promotion leaves the last good channel unchanged. Preserve state written by earlier releases, ownership, evidence and budgets. No separate channel-rollback workflow or live rollback rehearsal is required.

## Consumer execution and candidate testing

Provide a thin composite setup Action at `.github/actions/setup-cli`, usable as `kevinmartin/sofa/.github/actions/setup-cli@v0` (eventually `@v1`). Sofa's reusable workflows use the same Action internally; consumers can also use it directly in their own jobs. It downloads and verifies the selected released bundle, installs both CLIs on `PATH`, and exposes a `version` output. Install once per job so subsequent steps reuse the same binaries. The same Action builds explicit source selections locally in each job before step-scoped credentials are supplied.

**Released mode:** with `version` omitted or set to `v0`, each job that uses the CLIs resolves the workflow's major tag when its binary preparation starts and identifies the immutable semantic-version release it currently promotes. Download both CLIs from that release and keep that selection throughout the job. Later jobs, including rerun jobs, may select a newer compatible release within the same major.

The setup Action and CLI-using reusable workflows accept one optional `version` input. It accepts a major channel (v0 or eventually v1), an exact semantic release (v0.1.3), or a full lowercase source SHA. Empty selects the default major. An exact release selects that immutable Sofa release; v0 reusable workflows enforce v0 as their major boundary. The Action outputs the exact selected version for optional cross-job handoff; other workflows keep automatic per-job updates.

This selects the latest promoted binaries even when an older workflow revision containing release-selection logic is being rerun. Compatibility tests must therefore exercise newer CLIs with earlier release-aware workflows, including full, failed-job, and specific-job reruns. GitHub resolves the reusable workflow reference again for a full rerun, but retains its original commit for failed-job and specific-job reruns. A retained pre-migration workflow cannot adopt release selection retroactively; start a new run or rerun all jobs to adopt the updated major-channel workflow. [GitHub rerun behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations#behavior-of-reusable-workflows-when-re-running-jobs)

Verify the downloaded bundle using GitHub’s signed immutable-release attestation:

```sh
gh release verify-asset "$RELEASE_TAG" "$BUNDLE_PATH" \
  --repo kevinmartin/sofa
```

This verifies the asset’s digest against the signed release record. No consumer-maintained checksum, SHA allowlist, separate checksum-verification step, or custom signing key is required. Verification failure stops installation. Additional build-workflow attestations are deferred. [GitHub asset verification](https://cli.github.com/manual/gh_release_verify-asset)

Normal caller example:

```yaml
jobs:
  lifecycle:
    uses: kevinmartin/sofa/.github/workflows/lifecycle.reusable.yml@v0
    secrets:
      SOFA_PROJECTS_TOKEN: ${{ secrets.SOFA_PROJECTS_TOKEN }}
```

Direct Action use with an optional version handoff:

```yaml
jobs:
  first:
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.sofa.outputs.version }}
    steps:
      - id: sofa
        uses: kevinmartin/sofa/.github/actions/setup-cli@v0
      - run: sofa --version
  next:
    needs: first
    runs-on: ubuntu-latest
    steps:
      - uses: kevinmartin/sofa/.github/actions/setup-cli@v0
        with:
          version: ${{ needs.first.outputs.version }}
      - run: sofa-test --version
```

**Candidate mode:** a nonempty full commit SHA in `version` selects source compilation through the same setup Action. Each CLI job checks out that exact Sofa source without persisted credentials, verifies the checkout and builds both binaries locally. Strip GitHub token environment variables during builds and supply Project, model and publication secrets only to their later CLI steps. There is no candidate binary upload/download or separate candidate-build workflow. Kevin explicitly approved this per-job source path during PR #22 review.

The override selects binary source, not workflow YAML. Hosted E2E must select the candidate reusable workflow revision and pass its corresponding source SHA. Preserve secretless hosted jobs, exact PR head/base binding and existing publication boundaries; discovered PRs and issue text cannot authorize candidate execution with publication credentials. Normal consumers require neither Go nor an expiring controller artifact.
Migrate disposable callers, examples, schema URLs, and managed caller templates to major-channel usage. Retire the ordinary consumer dependency on `controller-build.reusable.yml`, retaining a legacy wrapper during migration where needed. Keep Sofa’s local quality-workflow call so PR checks exercise proposed quality changes.

Add `--version` and a machine-readable version command to both CLIs. Do not introduce another binary.

## Compatibility, acceptance, and rollout

The v1 promise covers workflow inputs/outputs and credential requirements, CLI arguments and machine-readable results, supported configuration, and upgrades of existing durable state. Compatible releases within a major must cooperate across jobs in the same run, including consumption of each other's outputs and shared state when jobs are retried. Human-readable logs and internal Go packages are outside that API promise.

Milestone 02.1 establishes compatibility fixtures. During v0, automatic promotion must preserve the enrolled consumer baseline; intentional breaking transitions require an explicit migration decision.

Required tests and hosted scenarios:

- **Release installation:** direct Action consumers and Sofa's reusable workflows use the same installer; both binaries run on `PATH` across subsequent steps without a Go toolchain or controller-build dispatch.
- **Automatic updates:** advancing the major tag updates an unchanged consumer on its next CLI-using job, including later jobs in an ongoing run.
- **Older workflows and reruns:** an earlier release-aware workflow revision successfully uses the newly promoted CLI. Cover full, failed-job, and specific-job reruns with GitHub's workflow-revision behavior; do not promise release selection from retained pre-migration workflows.
- **Major isolation:** v0 never selects v1; v1 never selects v2, including explicit `version` requests. Automatic selection never chooses an unpromoted release.
- **Optional version handoff:** a job outputs its exact release; after the channel advances, a dependent job requesting that version still downloads and verifies the original release. Reject conflicting release/source inputs and invalid version requests.
- **Mixed-version compatibility:** promote between jobs so one uses version A and another uses version B; prove compatible outputs, configuration, and shared state, including retries. Both CLIs in an individual job remain on the same selected release throughout that job.
- **Signed verification:** altered assets, missing attestations, or failed verification prevent execution.
- **Candidate mode:** the exact requested source is built; candidate jobs receive no Project, publication, or real model credentials.
- **Release failures:** interrupted publication, failed canaries, competing promotions, and retries preserve the existing usable channel.
- **Upgrade and forward recovery:** existing configuration, checkpoints, ownership, and counters survive supported upgrades and newer releases containing reverted code. Retain downgrade fixtures as compatibility coverage; they do not require a channel rollback or a separate recovery workflow.

For premerge acceptance, test release selection, verification failure handling, and promotion behavior with deterministic fixtures and fake release responses. Hosted E2E in `sofa-disposable` builds the exact candidate Sofa SHA from source. Normal consumer runs download real releases exclusively from `kevinmartin/sofa`; do not introduce disposable test releases, test channel tags, or a release-repository override. Record fixture and source-build evidence separately from actual release-download evidence. Inspect existing refs and release settings before migration.

Validate Go changes, workflows, generated templates, and both binaries. Record actual release/run references, measured timings, and limitations in the milestone evidence report. Initial v0 activation follows the owner-approved Sofa merge; milestone 10 retains integrated qualification and explicit v1 activation.
